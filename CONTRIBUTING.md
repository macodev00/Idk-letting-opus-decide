# Contributing to repo-ready

Thanks for taking the time to contribute! Every bug report, idea and pull request helps.

## Reporting bugs and requesting features

- Search [existing issues](https://github.com/macodev00/Idk-letting-opus-decide/issues) first — someone may have reported it already.
- For bugs, include what you did, what you expected, what happened instead, and your environment (OS, versions).
- **Security issues:** please do not open a public issue. Follow [SECURITY.md](SECURITY.md) instead.

## Development setup

`repo-ready` has no runtime or development dependencies. You only need Node.js 18 or newer.

```sh
npm install
npm run lint
npm test
node bin/repo-ready.js .   # run the CLI on this repository
```

## Project layout

| Path | Purpose |
| --- | --- |
| `src/checks.js` | Every check: id, severity, description and a `run(ctx)` function |
| `src/secrets.js` | Secret-scanning rules |
| `src/fix.js`, `src/templates.js` | Files generated by `--fix` |
| `src/reporters.js` | Text, JSON, Markdown and SARIF output |
| `src/action.js`, `action.yml` | The GitHub Action |
| `templates/licenses/` | License texts from choosealicense.com |
| `test/` | Tests (`node:test`) |

## Adding a check

1. Add an object to the `checks` array in `src/checks.js`. `run(ctx)` returns `pass(message)`, `fail(message, { details })` or `skip(message)`. Use `ctx.find(...)`, `ctx.match(regex)` and `ctx.read(file)` to inspect the repository.
2. If the problem can be fixed by creating a file, add a fixer in `src/fix.js` and its template in `src/templates.js`.
3. Add tests in `test/audit.test.js` and a row to the Checks table in the README.

## Adding a secret pattern

Add a rule to `RULES` in `src/secrets.js` and a test in `test/secrets.test.js`. Build fake tokens from pieces at runtime (for example `'ghp_' + 'x'.repeat(36)`) so the test file doesn't trip secret scanners. Please keep patterns specific: false positives erode trust faster than misses.

## Pull requests

1. Fork the repository and create a branch from the default branch.
2. Make your change. Add or update tests when you change behavior.
3. Make sure the test suite passes and the linter is happy.
4. Update documentation (README, CHANGELOG) if needed.
5. Open a pull request describing **what** changed and **why**.

Small, focused pull requests are reviewed faster than large ones. If you plan a big change, open an issue first so we can agree on the approach.
